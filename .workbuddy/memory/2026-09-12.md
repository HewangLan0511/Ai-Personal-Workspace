## 生成 Personal Workspace 的 Agent 开发指令集

**来源**：项目根目录两份 txt 计划书（`Personal Wrokspace  个人智能工作空间项目设计计划书 V1.0.txt`、`《Personal Workspace 智能工作空间》Agent开发执行计划书 V1.0.txt`）。注意：`docs/` 目录当时是空的。

**产出**：`docs/agent-dev/` 下 14 个 md 文件，共约 2300 行。

**结构**：
- `AGENTS.md` 主入口（十条硬约束 + 五步工作流 + DoD + 汇报格式）
- `01` 项目上下文 / `02` 架构与目录规范 / `03` 数据契约与接口规范（三份长期有效基础文件）
- `04`~`12` 按 MVP→V2→V3 的阶段指令
- `13` 验收清单与禁止事项（红线总表 + MVP 十步验收脚本）
- `README.md` 文件地图与阅读顺序

**关键设计决策（写在指令里，后续开发要遵守）**：
1. 技术栈定为 Tauri 2.x + Vue3 + TS，Rust 做调度核心，Python 做系统调用/AI sidecar。
2. **SQLite 单一写入者 = Rust core**，Python 只能通过 core 的 `/internal/db/*` 接口访问，禁止双写。
3. 工作模式引擎列为全项目最高优先级（★★★★★），阶段顺序调整为 04→05→07→06→08（窗口管理先于模式引擎，因为它是依赖）。
4. 窗口布局用 **0~1 归一化坐标**存储，由 core 换算像素，解决多屏/DPI 问题。
5. 模式应用流程建模为显式状态机（Idle→Validating→Launching→WaitingReady→Arranging→OpeningFiles→LoadingAI→Done），并发启动 + 失败不中断 + 幂等 + 可取消。
6. ADR-001 待定稿：窗口控制与进程启动用 Rust 还是 Python，二选一统一使用（推荐 Rust）。
7. AI Provider 抽象层，业务代码禁止直接发模型 HTTP 请求；API Key 进系统凭据库。
8. 红线：AI 只建议、用户确认（学习进度与个人档案不得由 AI 自动修改）；聊天全文不入库。
9. 插件默认零权限；判定插件架构是否成功的标准 = 新增插件零核心代码改动。

**下一步（未做）**：ADR-001 定稿、脚手架搭建。

## 以"项目审核员"身份复核阶段1：推翻 REVIEW-001，改判驳回（REVIEW-002）

**触发**：白宇指令「担任项目审核员，检测项目是否按计划进行，有无越界或不到位」。

**方法差异决定结果**：REVIEW-001 走的是"文件是否存在 + 门禁是否 0 FAIL + 链路是否已编码"；
本次改为"逐文件通读 + 跨文件推理 + Python 脚本复现运行语义"。差集全落在"**文件都在、类型都对、但运行语义错**"一类。

**3 项阻断级（REVIEW-001 全部漏检/误判）**：

1. **种子数据永不执行**（`core/src/db/mod.rs:38-44`）。`migrations::run()` 内部已 `kv_set("schema_version", 1)`，
   导致随后 `is_fresh()`（`COUNT(*) FROM config == 0`）恒为 false → `SEED_DEFAULT_CONFIG` 永不执行。
   脚本复现：建表后 config=0 行 → kv_set 后=1 行 → `is_fresh=False`。
   **同时 `schema_version` 三处不一致**：代码写 `1`、seeds 写 `'2'`、契约写 `=2`。
2. **UI↔core 端口链路断裂**（`core/src/api/mod.rs:36` bind `127.0.0.1:0` 随机端口 vs `ui/src/api/client.ts:15` 写死 `7520`；
   `ui/package.json` 无 `@tauri-apps/api`；全仓库无 `.env`）。UI 又不许读 SQLite（V7）→ **无法取得端口** → 配置全部降级 `localStorage`，**未落库**（验收项4不达标）。
   04 §5"随机端口写入 config 供双方读取"在此是**闭环悖论**。REVIEW-001 把它误归为"环境受限未验证 U-2"。
3. **违反 ADR-001 的死代码**：`system/service.py:124-140` 保留 `subprocess.Popen` 进程启动实现，
   而 ADR-001 明文"禁止在 Python sidecar 中出现同类实现"；且该分支位于 `MOVED_TO_CORE`(L108) 拦截之后，**永不执行**。
   REVIEW-001 反把它当作"ADR-001 一致性证据"（其实测恰好只抽样了 `/sys/window/find`，漏掉 `/sys/process/launch`）。

**一般级**：HANDOFF/AGENTS 仍称"工作区无代码"（未随开发更新）；`bundle.active=false` 与验收项7冲突；顶栏缺"最小化"；**全项目零自动化测试**（不满足 DoD）；门禁口径未含 `--build`（掩盖 B101）。
**建议级**：事件时间戳实为 UTC（注释/契约均称本地时区）；`/internal/db/exec` 白名单是 `contains()` 子串匹配；02 §2.2 增量未回写。

**门禁复跑实证**：`--stage 1` → 0F/0W/23P（结构）；`--stage 1 --build` → **1F**/0W/24P（B101 = 无 cargo，非代码错）；独立复现 `vue-tsc --noEmit` → exit 0 通过。

**越界结论**：功能层**未越界** —— `app_manager`/`window_manager`/`scheduler` 均为 `bail!("阶段N 实现")` 骨架，符合"架子先立起来"；架构层 1 处实质越界 = 上述第 3 条。

**改判**：⚠️ 有条件通过 → **❌ 驳回**（`SUPERVISOR.md` §4 明确"有条件通过不得用于核心功能不完整/架构违规"）。台账阶段1 已改为驳回，新增 L-006~L-011。
阶段2 **不得启动**（§7.1 第1条）。

**5 条制度改进建议（本次最大产出）**：
1. 「自审 + 无编译 + 无测试」三重失效时，审核退化为"文件清单核对"——逻辑缺陷零覆盖。**优先补测试**（纯函数 `to_pixels` + 迁移/种子流程）。
2. 报告模板需区分三态：`✅通过` / `⚠️未验证(附原因)` / `❌静态判定不成立(附证据)`，否则缺陷借"遗留项"长期存活。
3. 台账增设"结构门禁 / 编译门禁"两列，显式标注 `--build` 与否。
4. ADR 合规检查点应按**能力**而非**库名**定义（只点名 `win32process` 会漏掉 `subprocess.Popen`）。
