## 白宇实测抓到第二个真 bug（20:36~20:45）· 插件桥 targetOrigin 方向错

- **现象**：插件装上了、iframe 里 UI 渲染出来了，但"加载超时（10s 未报告 ready）"+ 崩溃 1 条。
- **根因**：示例插件 `window.parent.postMessage(msg, 'http://pwplugin.localhost')` —— postMessage 第二参校验的是**接收方（父窗口）**的 origin（生产态 = http://tauri.localhost），写成了 iframe 自己的 origin ⇒ 消息被浏览器**静默丢弃**。宿主侧 reply 用 ev.origin 原路回，正确无需改。
- **为什么之前测不出**：verify_stage9 是 HTTP 级验收，iframe 内真实 postMessage 属"UI 运行时"盲区（6/8 项 honest declaration 正是这一类）——白宇是真跑 iframe 的第一人，一击即中。
- **修复**：4 份 index.js（仓库源码×2 + %APPDATA% 已安装副本×2）targetOrigin 改 '*'（宿主侧有 origin 校验 + source 反查，安全）+ plugin-dev-guide.md 示例更正 + 桌面 zip 重打。UI/core 无需重编，白宇点"重试"重载 iframe 即生效。
- **教训**：postMessage 的 targetOrigin 是"对方是谁"不是"我是谁"——这类方向性语义错误，HTTP mock 永远测不到，只有真 iframe 能暴露。验收脚本声明"未实测"的地方，就是等着被人踩的地方。

## 第二坑：宿主 origin 校验拒收 opaque origin（20:45~20:50）

- 白宇重试后仍超时 → 第二层：pluginHost 死认 `ev.origin === 'http://pwplugin.localhost'`，但 sandbox 无 allow-same-origin 的 iframe 是 **opaque origin，ev.origin 序列化为 "null"**（那是文档的加载 URL，不是它的 origin）。两个坑叠一起：插件侧 targetOrigin 错 + 宿主侧收不进。
- **修复**：handleMessage 接受 `PLUGIN_ORIGIN || 'null'`；reply 的 targetOrigin 改 '*'（目标窗口已被 knownFrames 限定）。**安全主边界 = knownFrames source 反查**（伪造页面拿不到 pluginId），origin 校验只是辅助——原注释"opaque origin 的 origin 即此值"是错误假设，已订正。
- UI 嵌 exe ⇒ 必须重打（20:50 双包完成）。**注意：插件 JS 的修复不用重装（数据目录），但宿主修复必须换 exe**。
- 教训：**opaque origin 的 postMessage origin 是 "null"**——设计时想当然写进了注释还写进了验收假设。第三次验证：真窗口人工测试是独立的验收维度，躲不掉。
