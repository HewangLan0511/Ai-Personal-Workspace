## 决策

**选择方案 A：Rust（`windows` crate）实现窗口控制与进程启动。**

项目内**统一**使用 Rust 实现以下能力，**禁止**在 Python sidecar 中出现同类实现（`pywin32` 的窗口/进程操作）：

| 能力 | 归属 |
|------|------|
| 进程启动（CreateProcessW） | `core/app_manager`（Rust） |
| 窗口枚举 / 查找（EnumWindows 等） | `core/window_manager`（Rust） |
| 窗口定位 / 激活 / 置顶（SetWindowPos 等） | `core/window_manager`（Rust） |
| 窗口句柄持有与生命周期 | `core/state`（Rust） |
| 应用状态检测（进程存活） | `core/app_manager`（Rust） |

Python sidecar（`system/`）保留的系统能力（与窗口/进程**不重叠**）：
- 媒体会话（SMTC）、性能计数（CPU/GPU/内存）、AI Provider 调用、注册表扫描（已安装软件发现）。
- `system/win/` 下**不得**出现 `win32gui` / `win32process` / `win32api` 的窗口或进程操作。

## 理由

1. **核心能力不依赖易碎依赖链**：窗口调度是本项目的核心创新（工作模式引擎的执行末端）。若由 Python 实现，sidecar 崩溃 = 窗口功能整体失效；sidecar 冷启动（Python 解释器 + import）还会拖慢模式切换的 20s 硬指标。
2. **句柄生命周期管理**：窗口句柄（HWND）需要长期持有、跨模块读取，Rust 常驻进程内管理最稳。
3. **时序确定性**：模式应用是"启动→等就绪→定位"的流水线，Rust 侧无 GC/解释器抖动，重试与超时逻辑更可控。
4. **样板代码成本可接受**：`windows` crate 的 API 声明齐全，主要成本是一次性封装（阶段3 一次性投入约 4 个函数封装，之后全项目复用）。

## 代价与对策

| 代价 | 对策 |
|------|------|
| Windows API 样板多 | 封装成 4 个纯能力函数（find / set / activate / monitor-info），其余代码只调函数 |
| Rust 开发迭代慢于 Python | 窗口管理有完整单元测试（布局计算为纯函数），降低回归风险 |
| 本机暂无 Rust 工具链（2026-09-12 实测：cargo/rustc 不存在） | **编译验证延后**：源码先交付，待安装 Rust + MSVC 工具链后跑 `cargo check` 与 `tauri build` 作为补验项，登记遗留 |

## 合规检查点（写入门禁的依据）

- `system/win/` 中出现 `win32gui|win32process|win32api` 的窗口/进程调用 → 违反本 ADR，按架构违规处理。
- `core/` 中的窗口/进程实现出现 Python 调用（HTTP 转发到 sidecar 做窗口操作）→ 同上。
