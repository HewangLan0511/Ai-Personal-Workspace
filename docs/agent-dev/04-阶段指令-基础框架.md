# 04 · 阶段指令 · 第一阶段：基础桌面框架

**优先级**：P0 · MVP
**前置**：无
**依赖产出**：后续所有阶段都建立在本阶段骨架上

---

## 目标

建立软件骨架：应用能启动、能切页面、能保存配置。

**验收一句话**：双击图标启动 → 看到 Dashboard → 点左侧导航能切到各页面 → 改一个设置重启后还在。

---

## 必须实现

### 1. 工程脚手架
- 用 Tauri 2.x + Vue3 + TS 初始化，目录结构**严格**按 `02-架构与目录规范.md` 第 2.2 节。
- 配置 `tauri.conf.json`：窗口默认 1280×800、最小 1024×640、标题 `Personal Workspace`。
- 禁用开发环境以外的 devtools。

### 2. 主窗口布局
```
┌──────────────────────────────────────────────────┐
│  Logo                       [设置] [最小化]      │  ← 顶栏（可自定义标题栏）
├────────┬─────────────────────────────────────────┤
│Dashboard│                                        │
│  AI    │            内容区域                     │
│ 学习   │        （路由视图，按导航切换）         │
│ 项目   │                                        │
│ 档案   │                                        │
│ 生活   │                                        │
│ 设备   │                                        │
├────────┴─────────────────────────────────────────┤
│  状态栏：当前模式 / 运行中应用数 / 设备简况       │
└──────────────────────────────────────────────────┘
```
- 左侧导航可折叠，折叠状态持久化。
- 路由：`/dashboard` `/ai` `/learning` `/project` `/profile` `/life` `/device` `/settings`。
- 保留 `/plugins` 路由占位（V3 实现）。

### 3. Dashboard（Widget 卡片系统）★
**设计原则：Dashboard 不是信息堆积页，是控制中心。**

- 每个模块 = 一个独立 Widget，结构：
```ts
interface Widget {
  id: string
  name: string
  size: 'small' | 'medium' | 'large'   // 占 1×1 / 2×1 / 2×2
  position: { row: number; col: number }
  priority: number                      // 越大越靠前、展示越大
  enabled: boolean
}
```
- **动态布局**：根据使用频率自动调整。规则：
  - 记录每个 Widget 的点击/使用次数 → 存 `config` 表
  - 高频（`priority` 高）→ 用 `large` 展示；低频 → 收成 `small`
  - 用户手动调整过位置后，**以用户设置为准**，不再自动覆盖（`layout_locked = true`）
- 用 CSS Grid 实现，拖拽排序（V1 可先做点击"上移/下移"，拖拽放 V1.1）。

**V1 必须先有的 Widget**：
| Widget | 内容 | 优先级 |
|--------|------|--------|
| 当前项目 | 最近项目的名称/路径/快捷入口 | 最高 |
| 工作模式 | 模式卡片列表，点击即进入 ★ | 最高 |
| AI 助手 | 快捷提问入口 + 最近会话 | 高 |
| 常用软件 | 按 `launch_count` 排序的图标网格 | 高 |
| 学习路线 | 当前学习目标进度条（V2 填充数据） | 中 |
| 天气 | 天气简况 | 低 |
| 设备状态 | CPU/内存简况 | 低 |

### 4. 配置系统
- 配置读写统一走一层 `ConfigService`（Rust 侧），前端通过 API 访问。
- 存储：SQLite `config` 表（KV，value 为 JSON）。
- 必须支持：默认值、类型校验、变更广播 `CONFIG_CHANGED` 事件。
- 设置页面至少覆盖：主题（浅色/深色）、开机自启、默认 AI Provider、数据目录、隐私开关。

### 5. Python sidecar 打通
- `system/service.py` 提供 `/health`，由 Tauri 在启动时拉起并做健康检查。
- 通信走 `127.0.0.1` 随机端口（写入 `config` 供双方读取），**不要用固定端口**。
- 启动失败要有明确提示，且**不影响主界面可用**（降级模式）。
- 打包时用 PyInstaller 打成单文件，作为 Tauri sidecar 资源。

## 技术决策（ADR-001，必须在此阶段定稿）

**决策点：窗口控制与进程启动用 Rust 还是 Python 实现？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. Rust（`windows` crate） | 常驻、无额外进程、句柄持有稳 | Windows API 样板代码多 |
| B. Python（`pywin32`） | 开发快、生态熟 | 依赖 sidecar 存活 |

**要求**：
1. 二选一，**项目内统一，禁止混用**。
2. 把决策结果和理由写进 `config/app.toml` 注释 + 模块 README。
3. 若选 B，则必须实现 sidecar 崩溃自动重启，否则窗口功能会整体失效。

> 推荐 A：窗口调度是核心能力，依赖一个可能挂掉的 Python 进程不划算。

## 验收标准

| # | 验收项 | 方法 |
|---|--------|------|
| 1 | 应用能启动 | `npm run tauri dev` 无报错，窗口出现 |
| 2 | 启动速度 | 冷启动到 Dashboard 渲染完成 < 3s |
| 3 | 页面切换 | 点 7 个导航项都能正常切换，无白屏 |
| 4 | 配置持久化 | 改主题 → 重启 → 主题仍是改后的值 |
| 5 | sidecar | `/health` 返回 200；手动杀掉 sidecar 后应用仍可用 |
| 6 | 数据库 | 首次启动自动建库并执行 migration，`config` 表存在 |
| 7 | 构建 | `npm run tauri build` 能出安装包 |
