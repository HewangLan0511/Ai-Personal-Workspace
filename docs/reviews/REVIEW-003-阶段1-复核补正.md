## 二 · 补正发现（新证据）

### 🔴 C-01 · 04 §3「Dashboard（Widget 卡片系统）★」的**动态布局完全未实现**

`04` §3 是该阶段的 ★ 核心项，原文要求：
> - **动态布局**：根据使用频率自动调整。规则：
>   - 记录每个 Widget 的点击/使用次数 → **存 `config` 表**
>   - 高频（`priority` 高）→ 用 `large` 展示；低频 → 收成 `small`

**实测证据**：
```
=== autoSize 调用点 ===
  ui/src/stores/widgets.ts:72  autoSize(id: string, useCount: number) {     ← 仅定义处，无调用

=== 使用次数记录机制 ===
  useCount     -> 仅存在于 widgets.ts:72/76 的函数签名与局部变量
  use_count    -> 无
  clickCount   -> 无
  usageCount   -> 无
  launch_count -> 无   （frontend 侧）

=== widgets store action 的外部调用点 ===
  moveUp         -> DashboardView.vue:10,24 · useWidgets.ts:7,12      ✅ 已接线
  moveDown       -> DashboardView.vue:10,25 · useWidgets.ts:8,13      ✅ 已接线
  toggleEnabled  -> 【无外部调用】
  autoSize       -> 【无外部调用】
```

**结论**：
1. **没有任何"Widget 使用次数"的记录代码**——既不落 `config` 表，也不在内存计数。
2. `autoSize()` 是一个**孤儿函数**：定义了频率→尺寸的映射规则，但**全项目零调用**。
3. `useWidgets.ts` 顶部注释自称"上移/下移 + **自动尺寸**"，但其返回值**只暴露 moveUp/moveDown**——注释与实现不符。
4. 故 04 §3 的"动态布局"实际只剩"按 `priority` 静态排序"（`ordered` getter），**自动调频能力不存在**。

**为何两份报告都漏**：REVIEW-001/002 都把"Widget 结构 `interface Widget`"与"CSS Grid + 上移下移"当成了 §3 全部，
未逐句比对 §3 的"动态布局"三条规则。这是"读到了标题没读到正文"。

### 🟠 C-02 · 04 §4「类型校验」未实现；`KEYS` 白名单是**死代码**，任意键可写

`04` §4 原文要求：
> 必须支持：**默认值、类型校验**、变更广播 `CONFIG_CHANGED` 事件。

**实测**：
```rust
// core/src/db/config.rs:33-42
pub fn set(&self, key: &str, value: Value) -> anyhow::Result<Value> {
    let old = self.get(key);
    let raw = serde_json::to_string(&value)?;     // ← 直接序列化落库
    self.db.kv_set(key, &raw)?;                   // ← 无类型校验、无键白名单校验
    let _ = self.bus.publish(CONFIG_CHANGED, ...);
    Ok(old)
}
```
```
=== KEYS 全项目引用点 ===
  core/src/db/config.rs:46  pub const KEYS: &[&str] = &[    ← 仅定义处，无任何引用
```
- **类型校验：不存在**（检索 `typecheck|validate_type|is_string|is_boolean` → False）。
- **`KEYS` 常量定义后从未被使用** → 注释"新增键必须在此登记，禁止散落"**无任何强制力**，`KEYS` 本身构成**死代码**。
- 后果：`PUT /api/v1/config/{任意key}` 可写入**任意键**到 `config` 表，无白名单、无类型约束。
  现阶段仅 `config` 一表、接口仅对内，危害有限；但"必须支持类型校验"是 04 §4 的明文要求，**未达标**。

### 🟠 C-04 · `ui/src/utils/logger.ts` 是死代码：`logger.*` 调用 **0 次**

```
=== 未被任何文件引用的模块 ===
  [未被引用] ui/src/utils/logger.ts

=== logger.* 调用次数 ===
  0
```
- 该文件定义了完整的日志 API（info/warn/error/dump + 200 条环形缓冲），但**全项目零导入、零调用**。
- 直接后果：`AGENTS.md` §5「日志统一走 logger，禁止 `console.log` 留在交付代码里」在形式上"合规"，
  实质是**代码里根本没有任何日志调用**——`gate.py` 的 Q001「console.log 残留」报 0 WARN，
  是**假阴性**：它无法区分"改用了 logger"与"压根没写日志"。
- `ui/README.md:28` 把"logger（无 console 残留）"列为成果项，属**以文件存在代替功能存在**。
- 另注：`logger.ts:21` 用 `new Date().toISOString()`（UTC，带 `Z`），与契约 §3.1「本地时区 ISO8601」不符（与 R-11 同类，前端侧）。

## 五 · 方法论纠错（比上述任何单条缺陷更重要）

1. **验收面必须覆盖四套清单**：`阶段指令` 的「必须实现」+「验收标准」+「交付物」，加 `13` 的「禁止事项」。

2. **"文件存在" ≠ "功能存在"**：C-01（孤儿函数）、C-02（未使用的 `KEYS`）、C-04（未被导入的 logger）三例同源。
   建议在审核规程中固化一条动作：**对每个"声称实现了功能"的符号，检索其调用点；零调用即为未接线。**
3. **门禁的假阴性必须被人工兜住**：`gate.py` 的 Q001 通过 ≠ 日志合规；H001 通过 ≠ 无死代码。
   机器门禁擅长"存在性/模式"，**不擅长"接线/语义"**——这部分只能靠人工，且必须有固定动作。
4. **审核方同样受审**：本报告即是对 REVIEW-002 的纠错。建议在台账增设"报告被纠错次数"，作为监制尽职度的自证指标
   （对应 `SUPERVISOR.md` §十一「这套制度如何自证有效」的第 1 条）。
