# Workspace 工作生命周期状态模型（TECH-04 §三 · **仅设计，不实现**）

> 日期：2026-09-15 · 状态：**设计稿**（本轮不含任何代码改动、不含任何 UI）
> 关联：`docs/tech/workspace-runtime.md`（TECH-02 数据层）· `docs/tech/tech03b-integration-prep.md` §三（快照接口）
> 前置约束：ADR-001（窗口/进程控制只在 Rust 侧）· TECH-04 §二（不移动窗口 / 不杀进程 / 不改外部软件状态）

## 零、这份文档解决什么

TECH-02 建好了工作空间 Runtime（工作空间 / 应用 / 模板 / 布局快照），
但它只会回答**"现在摆着什么"**，不会回答**"这件事做到哪一步了"**。
没有后者，就没有"恢复"的对象 —— 恢复一个布局容易，恢复**一件正在进行的事**才是有价值的。

所以先把这个概念定清楚：**一件工作从开始到归档，走过哪几个状态、每次迁移需要什么条件、
哪些事在任何状态下都不许做。** 本轮只写模型，不动代码。

## 一、状态集合（5 态 + 1 个前置态）

```
   ┌────────┐   选择模板 / 新建     ┌───────────┐  prepare 4 步全 ok  ┌─────────┐
   │  idle  │ ───────────────────► │ starting  │ ─────────────────► │ running │
   │ 无活动 │                      │  开始中   │                    │ 进行中  │
   └────────┘                      └───────────┘                    └────┬────┘
        ▲                                │                              │
        │                         失败/取消│                    用户暂停 / 系统中断
        │                                ▼                              ▼
        │                           ┌──────────┐                  ┌─────────┐
        │                           │ archived │ ◄─── 放弃 ────── │ paused  │
        │                           │ 已归档   │ ◄────────────────┤  暂停   │
        │                           └──────────┘   放弃            └────┬────┘
        │                                 ▲                            │
        │                                 │  用户归档 / 自动(N 天)      │ 恢复
        │                           ┌─────┴──────┐ ◄─── 标记完成 ───────┘
        └───────────────────────────│ completed  │
             下一次开始是**新记录**   │  已完成    │
                                    └────────────┘
```

**为什么是 5 态而不是 3 态或 9 态**

- 3 态（开始/进行/结束）不够：**"暂停"必须独立**。它是恢复能力唯一真正的用武之地
  —— "进行中"被打断是常态，"暂停"承载了"上下文还在、等会儿回来"这个语义。没有它，
  恢复只能靠"重启上次的布局"，那和"恢复一件事"是两回事。
- 9 态（再拆出 初始化/准备/收尾/取消中…）过头：那些是**一次迁移内部的阶段**，
  不是用户能感知的稳定状态。它们应该表现为 `starting` 的进度输出（现有
  `prepareWorkspace()` 的 4 步 + `onProgress` 已经能干这件事），而不是新增状态。
- `idle` 不是"第 6 个状态"，而是**不变量的一半**：它表示"当前没有活动工作"。
  有了它才能把"至多一件活动工作"写成一句可判的话（见 §四 不变量 1）。

## 二、状态定义

| 状态 | 中文 | 含义 | 是否"活动工作" | 是否可写 |
|------|------|------|----------------|----------|
| `idle` | 无活动 | 没有正在推进的工作 | — | — |
| `starting` | 开始中 | 正在读模板 / 布局就位 / 同步应用状态 | ✅ | ✅ |
| `running` | 进行中 | 用户在做这件事 | ✅ | ✅ |
| `paused` | 暂停 | 上下文保留，等会儿回来 | ✅ | ✅ |
| `completed` | 已完成 | 这件事做完了，成果物已记录 | ❌ | ✅（可再补成果物） |
| `archived` | 已归档 | 只读留档，不再变更 | ❌ | ❌（**终态**） |

`outcome`（终态的原因，不单独成状态）：`done`（正常完成）/ `abandoned`（用户放弃）/
`aborted`（开始阶段就失败）。

> **刻意不做"取消"这个状态**：取消真正的语义是"这件事不再做了"，那属于 `archived + outcome=abandoned`；
> 单独立一个状态会让"归档"多一条并行入口，且无法回答"取消后的记录还算不算成果"。

## 三、迁移表

| # | From → To | 触发 | 守卫（Guard） | 记录 | 副作用（**设计**，本轮不实现） |
|---|-----------|------|---------------|------|-------------------------------|
| T1 | `idle` → `starting` | 用户选模板 / 新建工作 | 无其他活动工作 | `startedAt` | 采一份**基线快照**（用于"放弃时还原"） |
| T2 | `starting` → `running` | `prepareWorkspace()` 4 步全 `ok` | 至少 1 个应用就位 | — | 记 `enteredRunningAt` |
| T3 | `starting` → `archived` | prepare 失败 / 用户取消 | — | `outcome='aborted'` | **不还原软件状态**（还没动过） |
| T4 | `running` → `paused` | 用户暂停 / 系统级中断（Cinema、全屏演示） | — | `pausedAt` + `pauseReason` | **窗口与进程一律不动**（见 §五 红线） |
| T5 | `paused` → `running` | 用户恢复 | — | 累加 `pauseTotalMs` | 可选：把布局拉回暂停前（需用户确认） |
| T6 | `running` → `completed` | 用户标记完成 / 自然完成（关联应用全部关闭） | — | `endedAt` + `outcome='done'` | 采一份**成果快照** |
| T7 | `paused` → `completed` | 用户直接标记完成 | — | 同上 | 同上（跳过恢复） |
| T8 | `completed` → `archived` | 用户归档 / 自动归档（N 天后） | 无未保存成果物 | `archivedAt` | 记录转为只读；快照留档 |
| T9 | `running`/`paused` → `archived` | 用户放弃 | — | `outcome='abandoned'` | **不删数据**，只标终态；可选还原基线 |
| T10 | `archived` → `starting` | 用户"再做一次" | — | 新记录 `derivedFrom=<旧 id>` | **不复活旧记录**（终态不可变），新建一条 |

配套的合法迁移矩阵（`✔` 合法，`✘` 必须被拒绝）：

| From \ To | starting | running | paused | completed | archived |
|---|---|---|---|---|---|
| `idle` | ✔ T1 | ✘ | ✘ | ✘ | ✘ |
| `starting` | ✘ | ✔ T2 | ✘ | ✘ | ✔ T3 |
| `running` | ✘ | ✘ | ✔ T4 | ✔ T6 | ✔ T9 |
| `paused` | ✘ | ✔ T5 | ✘ | ✔ T7 | ✔ T9 |
| `completed` | ✘ | ✘ | ✘ | ✘ | ✔ T8 |
| `archived` | ✔ T10（**新建**） | ✘ | ✘ | ✘ | ✘ |

> 拒绝方式：**显式报错 + 不改状态**（与 `ModelRegistry` 的"拒绝要原子"同口径），
> 不做静默兜底 —— 静默兜底会把"程序 bug"伪装成"用户操作成功"。

## 四、不变量（可断言，将来直接进 verify 脚本）

1. **至多一件活动工作**：`|{w : w.state ∈ {starting, running, paused}}| ≤ 1`。
   理由：活动工作隐含"布局归属"——两件同时活动，恢复时布局该听谁的无法回答。
2. **终态不可变**：`archived` 之后任何字段不得变更（唯一例外：由 T10 新建的**另一条**记录）。
3. **每次迁移带时间戳与原因**：`{at, kind, reason}` 三段齐备，缺一不可（可审计）。
4. **时间单调**：`startedAt ≤ enteredRunningAt ≤ endedAt ≤ archivedAt`，`pauseTotalMs ≥ 0`。
5. **状态与成果物一致**：`state='completed'` 或 `outcome='done'` 时，`artifacts` 允许为空
   （"学完了但没产出"是合法的），但 `endedAt` 必须存在。
6. **归档不等于删除**：`archived` 记录必须可列出、可读；删除是另一件独立的事（且有确认）。
7. **暂停不释放**：`paused` 期间不得关闭任何外部软件、不得移动任何系统窗口。

## 五、跨状态红线（与 TECH-04 §二 同口径）

任何状态下都禁止：

| 红线 | 为什么在这里也要写一遍 |
|------|------------------------|
| 不杀进程 | "归档"最容易被顺手写成"把关联软件都关掉"。归档是**数据动作**，不是进程动作。 |
| 不移动系统窗口 | 恢复布局属后续阶段的执行侧；状态机只**记录意图**，不落手。 |
| 不修改外部软件状态 | 暂停/完成/归档都不得改写别人进程里的东西。 |
| 不跨运行期复用 hwnd | 快照契约的 `hwnd` 是 volatile；归档记录只存**快照 id**，不存句柄。 |

## 六、三种模式的差异

三种模式共用上面那台状态机，差异在**字段扩展**与**迁移倾向**，不在状态集合
（这点很重要：状态集合一旦按模式分裂，跨模式的统计与归档就没法统一）。

### 6.1 字段扩展

公共核心字段（三种模式一致）：

```
{ id, mode, state, outcome?, startedAt, enteredRunningAt?, pausedAt?, pauseTotalMs,
  endedAt?, archivedAt?, pauseReason?, snapshotIds[], derivedFrom?, transitions[] }
```

各模式追加：

| 模式 | 扩展字段 | 说明 |
|------|----------|------|
| 学习模式 | `progress`（进度指针，如 `{unit, done, total}`）、`sessionIndex`（第几次学习）、`lastPosition` | 学习是**可中断且必须可续**的：`lastPosition` 决定"下次从哪继续" |
| 项目模式 | `milestones[]`、`artifacts[]`、`repoRef?` | 项目有**阶段**与**成果物**，完成判据强 |
| 日常任务 | `dueAt?`、`checklist[]` | 事务级，通常一次做完，`paused` 罕见 |

### 6.2 模式 × 状态 的差异矩阵

| 维度 | 学习模式 | 项目模式 | 日常任务 |
|------|----------|----------|----------|
| 工作单元 | 一次学习会话（分钟~小时，可番茄式） | 一段专注期（小时~天） | 一件具体事务（分钟~小时） |
| `paused` 频率 | **最高**（被打断是常态） | 中（多为外部打断） | 低（一般直接做完） |
| `paused` 的关键负担 | `lastPosition` 不丢 —— 丢了就等于白学 | 上下文快照要能**回到同一状态** | 几乎不需要 |
| `completed` 判据 | 目标条目达成（"看完 2 节"） | 成果物提交 / 里程碑达成 | 事务关闭（一次性） |
| 重复开始 | 高频（每天多次，T10 常用） | 中频 | 低频，且**通常不该重复**（重复=漏了归档） |
| 归档保留什么 | 进度与时长（用于复习曲线） | 成果物 + 最终布局 | "已完成清单"一条 |
| 对快照（§TECH-04 §二）的依赖 | **低**：学习窗口组合稳定（笔记 + 资料） | **高**：项目布局差异大，恢复收益最大 | 低：1~2 个窗口 |
| 放弃的语义 | "这次没学完" —— 常见，**不应记为失败** | 放弃成本高，`outcome='abandoned'` 需留原因 | 放弃 ≈ 不该存在（应直接删或归档） |
| 自动归档阈值建议 | 长（记录本身有价值，如 30 天） | 短（项目结束即归档，如 3 天） | 极短（如当天结束） |

### 6.3 被否掉的两种设计

- **❌ 按模式分裂状态集合**（如学习模式没有"完成"、只有"阶段"）：
  跨模式统计（"我这周完成了多少件工作"）立刻无法回答；归档也要分成三套。
  ⇒ 状态集合统一，差异只放字段与默认阈值。
- **❌ 把"暂停"实现为"关闭关联软件以省资源"**：
  违反 §五 红线（不杀进程），而且恢复成本从"回到布局"变成"重新启动 + 等就绪"，
  正好把 `paused` 的存在意义抹掉。暂停只冻结**上下文**，不释放资源。

## 七、与现有 Runtime 的映射（说明差距在哪，本轮不填）

| 状态机概念 | 现有能力 | 差距 |
|------------|----------|------|
| `idle` → `starting` | 尚无 | 缺"活动工作"这个实体（现在只有 workspace，没有"一段进行中的事"） |
| `starting` → `running` | ✅ `workspaceRuntime.prepareWorkspace()`（4 步真异步 + `onProgress`） | 结果里没有状态迁移记录；只有 `ok` |
| `running` | ✅ store 的 workspace / apps / layout | 缺 `state` 与时间戳字段 |
| `paused` / `completed` / `archived` | ❌ 完全没有 | 需要给 `WorkspaceRuntime` 加 `state` 字段（**属后续阶段，本轮不动**） |
| 布局留档 | ✅ `saveLayoutSnapshot()` / `loadLayoutSnapshot()` / `listLayoutSnapshots()` | 已有，够用 |
| 双窗口（真实系统窗口）留档 | ⚠️ `workspaceRuntime.snapshot.*`（TECH-04 §二）已有接口面 | 采集侧等 core 探针；`capture()` 现为 `dryRun` |

**本轮只做映射，不改 `store.ts` 的形状、不加 UI、不加动画**（TECH-04 的禁止项）。

## 八、落地顺序建议（供后续阶段取舍）

1. **先加"活动工作"实体 + 状态字段**（`WorkspaceRuntime.state` + 迁移记录），UI 不暴露 —— 纯数据层，
   用验收脚本驱动即可验证 §四 的 7 条不变量。
2. **再接状态迁移的执行侧**（暂停/恢复要不要动窗口）—— 必须等快照采集能跑（core 探针就绪）之后，
   否则"恢复"没有可恢复的真相。
3. **最后才考虑 UI**：状态本身需不需要一个显式入口，是产品问题；数据层不应为它先做妥协。
4. 「日常任务」模式的自动归档阈值（§6.2）应作为**配置项**而不是常量，便于用户调节。
